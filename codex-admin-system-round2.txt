# DouyinLiveRecorder 后台管理与监控系统扩展计划

## Context

当前项目是一个以 `main.py` 为核心的命令行直播录制工具，配置来自 `config/config.ini` 和 `config/URL_config.ini`，运行状态主要靠终端输出和日志观察。近期已新增 YouTube 自动上传能力，但上传记录仍以本地 JSON 状态文件为主，缺少图形化管理、任务监控、历史记录和数据报表。

目标是把项目逐步扩展成一个本机优先、用户友好的后台系统：用户可以在浏览器里配置录制参数、管理直播间、查看录制状态、查看上传记录，并查看 YouTube 视频播放数据报表。

## Product goals

1. 图形化配置：在网页后台配置直播间、录制格式、保存路径、代理、分段录制、YouTube 上传参数。
2. 录制监控：展示当前监控/录制任务、录制时长、文件大小、状态、最近错误，并支持开始/停止单个任务。
3. 上传记录：记录每个视频的上传状态、YouTube video id、标题、发布时间、失败原因、重试次数，支持手动重试。
4. 视频数据报表：第一版只拉取 YouTube Data API 可直接获取的基础指标，例如播放量、点赞数、评论数；观看时长、流量来源等 Analytics API 指标放到后续阶段。
5. 下载目录自动化：实时监控 `downloads` 或用户配置目录，发现稳定的新视频文件后自动进入编码与 YouTube 上传流程。
6. Douyin 采集下载：提供 API 触发的抖音单作品下载和用户主页公开视频批量下载，下载产物进入统一文件管理与后续上传链路。
7. 用户友好：避免用户直接编辑 ini 文件；敏感凭证只保存本地路径和有效性状态，不在前端明文展示。

## Process boundary

第一版明确采用“Web 后端 + 独立录制 worker 子进程”的边界，避免 FastAPI 直接 import 并调用 `main.py` 的全局状态。

- FastAPI 负责配置、任务命令、状态查询、数据库写入和前端 API。
- 录制 worker 负责实际录制、ffmpeg 子进程、直连 FLV 下载和录制完成事件。
- 后端通过数据库中的任务命令表或轻量本地 IPC 向 worker 下发 start/stop 请求。
- worker 把状态事件写回数据库：录制开始、探测中、录制中、停止中、文件生成、上传开始、上传成功、上传失败。
- Douyin 采集下载 API 作为后端服务能力运行，不直接 import `main.py`；采集核心放在独立模块，下载完成后通过统一文件登记/目录监控进入上传链路。
- CLI 可继续保留，但后台模式下数据库是权威来源；ini 只作为导入/导出兼容文件。

这样做的原因：当前 `main.py` 使用大量全局变量、线程和终端交互，同进程接入 FastAPI 容易造成状态污染、重复启动、阻塞和难以停止。

## Recommended architecture

采用渐进式改造，不一次性重写录制核心：

1. 保留现有录制逻辑作为 worker 内部的“录制引擎”。
2. 新增 FastAPI 后端，负责配置管理、任务控制、状态查询、上传记录、报表 API。
3. 新增 SQLite 数据库，作为后台模式的配置、任务、文件、上传记录和分析指标权威来源。
4. 第一版前端优先使用 FastAPI + Jinja/HTMX 或极简页面，减少构建复杂度；API 稳定后再引入 React/Vue SPA。
5. 逐步把 `main.py` 中的配置解析、直播间模型、录制完成事件抽到可被 CLI 和 worker 复用的模块。

## Phase 1: 数据库、状态机和后台 API 骨架

新增后端目录，例如 `server/`：

- `server/app.py`：FastAPI 应用入口和 lifespan。
- `server/db.py`：SQLite 连接、WAL 初始化和事务工具。
- `server/models.py`：数据表定义。
- `server/config_service.py`：导入/导出 ini，后台模式下以数据库为权威源。
- `server/recording_service.py`：创建任务命令、查询任务状态。
- `server/upload_service.py`：上传记录查询和失败重试。
- `server/download_watch_service.py`：实时监控下载目录，稳定文件检测、编码触发和文件登记。
- `server/douyin_collection_service.py`：抖音单作品/用户主页采集下载任务编排。
- `server/analytics_service.py`：拉取和缓存 YouTube 基础数据。
- `server/path_service.py`：统一路径规范化和下载目录边界校验。

首批数据表：

- `rooms`：直播间 URL、主播名、平台、清晰度、是否启用、创建/更新时间。
- `recording_jobs`：room_id、状态、开始时间、结束时间、错误信息、配置快照、关联 ID。
- `recorded_files`：job_id、room_id、本地绝对路径、大小、格式、分段序号、时长、创建时间、可选 checksum。
- `download_watch_records`：监控来源目录、文件 identity、稳定检测状态、编码状态、登记时间、错误信息。
- `douyin_collection_tasks`：任务类型(single/user_batch)、输入 URL、状态、max_items、进度、错误信息、创建/结束时间。
- `douyin_downloaded_items`：task_id、aweme_id、作者、描述、本地文件路径、来源 URL、下载状态、错误信息。
- `upload_records`：recorded_file_id 或 downloaded_item_id、本地文件 identity、YouTube video id、标题、隐私状态、状态、失败原因、重试次数、上传配置版本。
- `youtube_metrics`：video id、日期、播放量、点赞数、评论数、拉取时间。
- `settings`：全局录制设置、上传设置、下载目录监控设置、Douyin 采集默认设置。
- `task_commands`：后端发给 worker 的 start/stop/retry 命令及处理结果。

SQLite 约束：

- 启用 WAL 模式。
- 每个线程/请求使用独立连接。
- 写操作保持短事务。
- 统一通过 service/repository 层写入。
- 遇到 `database is locked` 做有限次数退避重试。

## Recording job state machine

录制任务状态枚举：

- `pending`：已创建，等待 worker 处理。
- `probing`：正在解析平台和直播源。
- `recording`：正在录制。
- `stopping`：用户请求停止，正在优雅收尾。
- `completed`：自然结束且文件已登记。
- `interrupted`：用户停止后文件已登记。
- `failed`：异常失败，无可用文件或需要人工处理。

允许迁移：

- pending → probing → recording → completed
- pending/probing/recording → stopping → interrupted
- pending/probing/recording/stopping → failed

幂等规则：

- 对正在运行的 room 重复 start，返回现有 active job，不创建重复任务。
- 对非运行任务 stop，返回当前状态，不报错。
- worker 重启后扫描 `pending/probing/recording/stopping` 的旧任务，标记为 `failed` 或根据已生成文件登记为 `interrupted`。

## Stop protocol

停止录制必须优先保证文件可用：

1. 后端写入 stop 命令，job 进入 `stopping`。
2. worker 对 ffmpeg 录制优先发送 `q`，等待固定超时时间。
3. 超时后再终止 ffmpeg 子进程，并记录是否生成可用文件。
4. 对直连 FLV 下载，设置停止标记，让下载循环退出并关闭文件句柄。
5. 停止后扫描已知输出路径和分段文件，登记到 `recorded_files`。
6. 如果启用上传，创建 `upload_records`，由上传 worker 继续处理。

## Configuration authority and migration

后台模式下数据库是权威来源。

迁移规则：

1. 首次启动后台时读取 `config.ini` 和 `URL_config.ini` 导入数据库。
2. 导入后 Web 后台只写数据库。
3. ini 文件只作为导入来源和手动导出目标，不做持续双写。
4. 如果用户手动修改 ini，需要在后台点击“重新导入”，并显示冲突预览。
5. CLI 继续使用 ini；后台模式使用数据库。两种模式不同时作为权威源。

## API contract for first version

首批 API：

- `GET /api/rooms`：返回直播间列表。
- `POST /api/rooms`：新增直播间；校验 URL、平台、清晰度。
- `PATCH /api/rooms/{id}`：编辑直播间配置。
- `POST /api/rooms/{id}/start`：幂等启动；如果已有 active job，返回它。
- `POST /api/rooms/{id}/stop`：幂等停止；如果未运行，返回当前状态。
- `GET /api/jobs`：按状态查询任务。
- `GET /api/files`：查询录制文件，支持 room/date/status 过滤。
- `GET /api/uploads`：查询上传记录。
- `POST /api/uploads/{id}/retry`：对 failed 上传记录重试。
- `GET /api/download-watch`：查询下载目录监控记录和最近处理结果。
- `PATCH /api/download-watch/settings`：配置监控目录、轮询间隔、稳定检测次数、是否转 MP4 后上传。
- `POST /api/douyin/download`：创建单个抖音作品/分享链接采集下载任务。
- `POST /api/douyin/user-download`：创建抖音用户主页公开视频批量采集下载任务，必须限制 `max_items`。
- `GET /api/douyin/tasks`：查询 Douyin 采集下载任务列表。
- `GET /api/douyin/tasks/{id}`：查询单个 Douyin 采集下载任务详情、进度、文件和错误。
- `GET /api/metrics/videos`：查询 YouTube 基础指标。
- `GET /api/events/recent`：查询最近事件流，方便排障。

错误处理：

- 400：参数非法，例如 URL 或路径不合法。
- 404：资源不存在。
- 409：状态冲突，例如配置冲突或命令已存在。
- 500：内部错误，但响应中不包含 token、cookie、client secret。

## Phase 1.5: 下载目录监控与 Douyin 采集下载

下载目录监控：

1. 后端提供 `download_watch_service`，按配置目录轮询扫描视频文件。
2. 文件必须通过稳定检测：连续多次检查 `size + mtime` 不变且非零大小后才进入处理。
3. 忽略 `.tmp`、`.part`、`.download`、`.crdownload` 等临时文件。
4. 对 `.mp4` 直接登记为可上传文件；对 `.ts/.flv/.mkv` 可按配置先转 MP4，再登记生成文件。
5. 文件 identity 使用规范化路径、大小、mtime 或 checksum，避免重复上传。
6. 下载目录监控只处理允许目录内文件，不读取任意系统路径。

Douyin 采集下载：

1. 新增独立采集核心模块，例如 `src/douyin_collection.py`，不复制 `erma0/douyin` 的 GPL 代码，只借鉴分层思路。
2. 支持单作品/分享链接：解析短链跳转，提取 `aweme_id`，获取作品详情，下载视频。
3. 支持用户主页批量：解析 `sec_user_id`，分页获取公开视频，按 `aweme_id` 去重，并强制 `max_items` 上限。
4. API 请求支持传入 Cookie 和代理，但 Cookie 不写入默认配置、不入库明文展示、不写日志。
5. 下载默认落到 `downloads/douyin/{author}/{aweme_id}_{desc}.mp4`，随后进入统一文件登记和上传链路。
6. 对风控、私密作品、空作品列表、下载地址为空等情况返回明确错误。
7. 第一版不绕过登录或风控，不做无限批量采集，不保证所有抖音接口长期稳定。

## Phase 2: 录制引擎适配顺序

按低风险边界拆分，不先重写主循环：

1. 抽配置解析：把 ini 配置读取转为纯函数/数据对象。
2. 抽直播间列表模型：把 URL 行解析转为可测试函数。
3. 抽录制完成事件：统一 `record_started`、`file_completed`、`record_failed`、`upload_changed` 事件。
4. worker 先复用现有录制流程，只在关键事件点写数据库。
5. 最后再考虑把 `start_record()` 拆成更小的可控制函数。

## Phase 3: Web 管理界面

第一版页面：

1. 仪表盘：当前录制数、今日生成视频数、上传成功/失败数、最近错误。
2. 直播间管理：新增、编辑、启用/停用、手动开始/停止录制。
3. 配置页面：录制格式、保存路径、代理、分段录制、YouTube 上传设置。
4. 文件与上传记录：查看文件、上传状态、YouTube 链接、失败重试。
5. 下载目录监控：查看最近发现的文件、稳定检测状态、编码状态、上传入队状态和失败原因。
6. Douyin 采集下载：提交单作品链接或用户主页链接，设置 `max_items`，查看采集进度、下载文件和错误。
7. 报表页面：按 video_id/date 展示 YouTube 基础指标；主播维度等房间与文件关联稳定后再做。

前端不直接访问本地文件和凭证，只通过后端 API 操作。

## Phase 4: YouTube 上传与数据分析

上传：

- 当前 `src/youtube_uploader.py` 的 JSON 状态迁移到数据库表 `upload_records`。
- `upload_records` 对 `recorded_file_id` 或稳定文件 identity 设置唯一约束，避免重复上传。
- 迁移脚本必须可重复运行；已迁移 JSON 记录要标记来源和迁移时间。
- 上传前创建记录，上传中更新进度，成功后写入 video id，失败后写入错误和重试次数。
- 下载目录监控和 Douyin 采集下载产生的 `.mp4` 文件，也通过同一套文件 identity 和 `upload_records` 去重机制进入上传队列。
- 后台页面支持对 failed 记录手动重试，超过最大重试次数需人工确认。

数据分析：

- 第一版仅使用 YouTube Data API 获取播放量、点赞数、评论数。
- YouTube Analytics API 作为后续 Phase 4.5：单独设计 scope、授权账户、数据延迟、失败降级和更细数据模型。
- 定时任务每天拉取一次指标并写入 `youtube_metrics`，避免每次打开页面都打 API。

## Background tasks and observability

- 使用 FastAPI lifespan 启动和停止后台任务。
- 用数据库租约或进程锁避免开发 reload/重复启动造成多个 scheduler 同时运行。
- 所有日志和事件记录带 `job_id`、`file_id`、`upload_id`，Douyin 任务带 `douyin_task_id`、`aweme_id`，方便从页面追踪一条采集/录制到上传的完整链路。
- 后台页面提供最近事件流：任务命令、录制状态、下载目录监控、Douyin 采集下载、上传状态、指标拉取错误。

## Path safety

- 所有用户输入路径统一经过 `Path.resolve()`。
- 保存到数据库前转为规范化绝对路径。
- 文件操作必须校验路径位于允许的下载目录或配置目录内。
- Windows 下要处理盘符、大小写和分隔符差异。
- Douyin 下载输出目录必须位于允许下载根目录内，用户传入 `output_dir` 时只允许相对路径或经过白名单校验的目录。
- 禁止 API 读取任意系统文件。

## Security and privacy

- OAuth client secret 和 token 文件不入库、不显示全文，只保存本地路径和是否有效。
- 后台默认只监听 `127.0.0.1`。
- 如果用户显式开启局域网访问，必须先加入登录认证。
- API 不返回 Cookie、OAuth token、client secret 的明文。
- Douyin 采集请求允许临时传入 Cookie，但 Cookie 只用于当前任务，不持久化明文，不进入事件日志。
- 日志中屏蔽敏感字段。

1. pytest：ini 导入、URL 行解析、路径边界校验、状态机迁移、SQLite repository 写入、上传记录迁移幂等性。
2. API 测试：rooms CRUD、start/stop 幂等性、jobs/files/uploads 查询、retry 行为、download-watch 设置和查询、Douyin 任务创建和查询。
3. worker 测试：用短时 mock/fixture 录制命令验证状态事件和文件登记。
4. 下载目录监控测试：慢速写入文件不提前入队，稳定后登记；临时后缀被忽略；重复文件不重复上传。
5. Douyin 采集测试：单作品链接解析、用户主页分页低限额采集、Cookie 缺失/风控错误提示、下载路径边界校验。
6. 前端冒烟：能打开仪表盘、房间列表、上传记录页、下载目录监控页、Douyin 采集任务页。

2. 从现有 ini 导入配置和直播间，前端能看到相同数据。

6. 提交一个 Douyin 单作品下载任务，确认任务完成、文件落盘并进入统一文件/上传链路。
7. 提交一个 Douyin 用户主页批量下载任务，`max_items=3`，确认进度、文件和错误可查询。
8. 触发 YouTube 上传，确认上传状态从 pending → uploading → uploaded/failed。
9. 重启后台，确认任务记录、上传记录和配置仍可查询。
10. 拉取 YouTube 视频基础指标，确认报表页面能按日期和视频展示数据。
11. 检查敏感信息不会在 API 响应和日志中泄露。
